# NyayaFlow code audit — 2026-10-29

This report compares the supplied workflow PDFs with the current working tree. The PDFs define planned statuses and acceptance behavior; the code and test runs below determine what is actually built. `docs/AUDIT.md` contains the older item-by-item matrix for requirements 1–108. This report adds the current architecture, Engine 11–15 coverage, current verification and fixes from this audit.

## Workflow summary

NyayaFlow (the application title and repository README also use “NagrikSetu”) is a human-reviewed grievance intake and routing prototype. A complaint can be submitted in English, Hindi or Hinglish; deterministic code extracts an issue and any supported location, proposes a department or abstains, and records a human decision history. Staff access is scoped by role, department and approved geography. Split complaints and duplicate incident links keep original complaint records. Demo records, geography and evaluation labels are synthetic. The three exact synthetic demo accounts can receive a city-wide Gwalior grant only when both demo flags are enabled; ordinary staff require geography-admin approval.

The workflow PDFs describe status as intent: BUILD means the feature should work end to end, TRY is experimental, MOCK is simulated, ROADMAP is not implemented, and REMOVED is explicitly out of scope. A document status alone is not evidence of implementation.

## Architecture map

- **Stack:** Python 3.12; Streamlit 1.66.1; SQLite; pandas 3.1.0; scikit-learn 1.9.1; Pillow 13.0.0; cryptography 50.0.2; Authlib 1.9.1; bcrypt 5.0.0; pytest 9.1.1. Version constraints are in `requirements.txt`.
- **Frontend and app entry:** `app.py` owns sign-in, role-aware navigation and the Streamlit multi-page shell. Public screens are in `pages/10_Public_Portal.py` and `pages/8_Request_Review.py`; staff screens include `pages/0_Home.py`, `pages/6_Inbox.py`, `pages/2_Review.py`, and `pages/11_Request_Review_Queue.py`. Engines 11–15 pages are `pages/13_Hotspots.py`, `pages/14_Correction_Dataset.py`, `pages/15_Model_Evaluation.py`, and `pages/16_Users_Roles.py`.
- **Backend/services:** `core/` contains intake, routing, splitting, ownership, duplicate, safety, ledger, authentication/RBAC, geography, attachments, hotspots, challenges, corrections and analytics. Streamlit handlers call these Python services in-process. There is no FastAPI/HTTP API, route table, API base URL or separate frontend/backend deployment.
- **Database/storage:** `db/schema.sql` defines the SQLite schema; `core/db.py::init_db` applies additive startup migrations. Default DB is `db/nyayaflow.db`, overridden by `NYAYAFLOW_DB_PATH`. Uploaded images are stored under `data/uploads` using random names and are AES-GCM encrypted only when `NYAYAFLOW_ATTACHMENT_KEY` is configured. SQLite complaint data is not encrypted at rest by this app.
- **Data and evaluation:** `data/complaints.csv` contains the grouped train/val/test routing data; `data/duplicate_pairs.csv` and its manifest hold a separate dev/test pair set. Keyword routing is in `core/router_baseline.py`; TF-IDF evaluation is in `core/router_ml.py`; `scripts/evaluate_full.py`, `scripts/evaluate_duplicates.py`, `core/safety.py::evaluate_safety_rubric`, and `core/verify_split.py` report checks.
- **Run:** from the repository root, use `python -m scripts.init_db`, then `python -m streamlit run app.py`. Use `python -m pytest -q` for the repository suite and `python -m scripts.run_acceptance` for the acceptance runner. Export variables from `.env.example` in the shell; the file is a reference and is not auto-loaded.

## Real data paths

1. **Public complaint:** Streamlit form → `pages/10_Public_Portal.py` validates typed/confirmed voice text and selected geography → `core/intake.py::process` preserves the original string and separately normalizes it → `core/router_baseline.py::route` returns candidates or abstains → `core/db.py::insert_public_submission` uses one `BEGIN IMMEDIATE` transaction for complaint, suggestion and initial `suggested` ledger event → the UI reports success only after commit. Optional photo storage is a second transaction; a photo-only failure is reported with a retry while the saved complaint remains available.
2. **Staff queue and review:** `core/staff_dashboard.py::list_staff_cases` → `core/geo.py::scoped_complaints` applies active identity, approved area, and operator department scope → suggestions and ledger history are loaded separately, so a missing suggestion does not remove an in-scope complaint → `pages/0_Home.py`/staff dashboard displays the queue → review or action services append ledger events. Abstained or missing-suggestion cases are visible to an in-scope reviewer; they do not acquire a department. Operators remain department-scoped, so an unassigned case is not in an operator department inbox.
3. **Citizen review request:** resident-owned case check → `core/portal.py::request_own_review` → `core/challenges.py::create_challenge` atomically creates an open request and ledger event → reviewer queue → `resolve_challenge` requires reviewer role and reason and records resolution plus decision event. The citizen request does not alter routing.
4. **Evaluation:** CSV family groups → frozen manifest and leakage check → TF-IDF fitted on train and threshold chosen on validation → baseline and TF-IDF assessed on the same frozen test rows. Duplicate threshold uses the dev pairs and test hash manifest. The held-out split was not modified during this audit.

## Shared contracts

- **IDs:** internal complaint key is SQLite integer `complaints.id`. Public case IDs are `CASE-` plus 12 uppercase hex characters; staff-assisted intake uses `CASE-` plus a full UUID hex string. Confirmed child issues reuse the parent case ID and store `parent_id`.
- **Complaint state:** there is no mutable complaint `status` column. The staff UI derives `new`, `pending`, `awaiting clarification` or `resolved` from the latest status-relevant ledger event and open challenge rows. Challenge status is `open` or `resolved`. The routing suggestion is not a final decision.
- **Ledger:** `complaint_id`, event type, actor, suggested/final department, reason/reason code, JSON details and UTC database timestamp. Relevant events include `suggested`, `accept`, `edit`, `clarify`, `escalate`, `transfer`, `dispatch`, `resolve`, `challenge`, `challenge_resolved`, split and duplicate-link events. SQLite triggers reject `UPDATE` and `DELETE` on `ledger`; `ledger_integrity` stores a chained SHA-256 digest per event and has its own append-only triggers. See [LEDGER_INTEGRITY.md](LEDGER_INTEGRITY.md) for genesis/backfill and limits.
- **Roles:** `public`, `operator`, `reviewer`, `auditor`; legacy `government` remains in compatibility policy. Permission checks load active identity/role from SQLite. Operators are department-scoped; staff are area-scoped; reviewers decide citizen requests; auditors are read-only. SQLite has no row-level security policy layer.
- **Request/response and errors:** no HTTP request/JSON response contract exists. Streamlit form callbacks call Python service methods. Services return dictionaries/lists or raise `ValueError`/`PermissionError`; UI success appears after persistence and exceptions render an error state.
- **Configuration:** `NYAYAFLOW_DB_PATH`; `NAGRIKSETU_DEMO_MODE`; `NAGRIKSETU_DEMO_SLA_DAYS`; `NYAYAFLOW_FEATURE_VOICE`, `_PHOTOS`, `_HOTSPOTS`, `_CITIZEN_REVIEW`, `_LEARNING`; `NAGRIKSETU_AUTH_SECRET`; `NYAYAFLOW_ATTACHMENT_KEY`; `NYAYAFLOW_TLS_CERT`, `NYAYAFLOW_TLS_KEY`; `NYAYAFLOW_GEO_ADMIN_EMAILS`. `.env.example` documents these; it is not auto-loaded.

## Rules R1–R10 and verified changes

- **R1:** review actions already rejected automatic closure/rejection/deprioritization, but the generic ledger service and database initially accepted those event labels. `core/ledger.py::log_event` now rejects prohibited final-action event types, and `db/schema.sql` adds an INSERT trigger so direct SQL cannot bypass the rule. Explicit reviewer resolution and human duplicate decisions remain available.
- **R2:** fixed intake validation that stripped surrounding whitespace. It now checks non-empty text without changing the submitted string; the 10,000-character ceiling is enforced in the intake service and both text areas. Regression tests cover whitespace, Devanagari, emoji and markup characters.
- **R3:** DB triggers block ledger and hash-sidecar UPDATE/DELETE; tests verify direct SQL failure. Corrections append new rows. Hash-chain checks detect ordinary content tampering but are not cryptographic signatures or a tamper-proof guarantee.
- **R4:** unknown location/area remains unknown or null. A user-selected geography is explicit input, not inferred fact.
- **R5:** abstained/missing suggestions are visible to in-scope reviewers. Operators remain department-filtered and geography access remains enforced.
- **R6:** citizen review request does not route. Model output is persisted as a suggestion; human final departments are ledger events. A suggestion may determine an operator's working inbox, so this remains a prototype routing aid.
- **R7:** evaluation and hotspot outputs carry synthetic/simulated labels and denominators. No real-city performance claim is supported.
- **R8:** manifest hash for the 27-row routing test split passes; group leakage check passes. No frozen test data was changed or used to tune thresholds in this audit.
- **R9:** public success is set only after complaint + suggestion + initial ledger transaction commits. Forced-write-failure UI test confirms no fake success. Photo failure is separated and retryable after complaint save.
- **R10:** no source in the repository describes the 23% reassignment figure as a misrouting rate.

## Remaining risks, highest first

1. **Access and live data:** no production identity, database row-level security, TLS verification, database encryption, retention/deletion policy or real municipal geography. Do not use real resident data.
2. **Routing and duplicate utility:** routing accuracy is weak and TF-IDF safely abstains on every held-out single-owner case; duplicate recall is zero on its small synthetic test. Human review is required.
3. **Ownership truth:** all 8 responsibility rules are assumptions, not verified Gwalior assignments.
4. **Voice:** real microphone/browser behavior and Hindi/Hinglish transcription quality are unverified.
5. **Photos:** feature works in tests with a key, but this environment disables uploads; production key lifecycle and backup are unresolved.
6. **Concurrency/idempotency:** Streamlit buttons do not use a submission idempotency token, and two reviewers can act on the same case sequentially. The tested workflow preserves both events, but no single-review lock is established.
7. **Coverage:** the prototype has no Open311/API integration, no low-bandwidth benchmark, no UI-language toggle, no offline save/resume, no cluster map, no cross-department shared thread, no what-if simulator and no live staff pilot.

No commits were created: `.git` is exposed read-only in this workspace. The working tree already contained unrelated user changes; this audit left them in place.
